# The absorption

What the audit found, what each frontend must change, and in what order.

The matrix and the inventory are mechanical and are regenerated by
`tools/audit_frontends.py`. This file is the reading of them: what the
numbers mean, which changes are safe, which are decisions, and which are
blocked.

---

## What the audit found

**One: the palette is already shared. The namespace is not.**

Eight of the ten frontends already carry the gnosix palette. They call it
`--gnu-anthracite`, `--paper`, `--ink`, `--corpus-neutral-950`,
`accent: #FF6A00` in a Rust token file, or `--gnu-beret` — but the colours
are the system's colours, to the byte. The gap between these repositories
is not taste. It is spelling.

**Two: where a frontend says `--gnosix-*`, it usually does not mean it.**

Two repositories ship a vendored copy of `gnu6-design 1.1.1` and so appear
to have adopted the namespace. Measured against what the system actually
publishes:

| | names | spelling | values |
|---|---|---|---|
| the design system publishes | 90 | — | — |
| the vendored copy declares | 21 | 6 identical, **15 different** | **21 identical, 0 different** |

Not one colour has drifted. Fifteen *spellings* have. And the copy carries
one colour in four of the ones the system publishes.

So the migration for those two repositories is the cheapest and the safest
in the whole programme: rename fifteen variables, add the sixty-nine the
system publishes and the copy omits, and change no value. No visual risk,
no regression to chase.

**Three: two frontends are not consumers at all.**

`spjoaillerie-live` is a capture of a storefront with its own brand —
Didot, Garamond, gold, parchment. `blob.in-showcase` is a native surface
with a cyan accent where the system has an orange one, and its theme file
claims to derive from a gnosix path whose palette is not the system's.
Neither is a design-system consumer. One is a different brand that should
be left alone; the other has a claim that has to be corrected before
anything else happens.

> **Correction, 2026-10-20.** This audit said the path does not exist. It
> does exist: `gnosix/crates/gnos-ux-gpui/src/product_design.rs` is there,
> and what it carries is a palette of its own — a cyan, and not one colour
> of the system's. The claim in the showcase's source is still false, and
> it is false for the other reason: the file it names is not the system's
> palette. The showcase stays out of the programme, and its sentence is
> corrected.

**Four: the component layer is the actual blocker.**

The system declares four components: `action`, `input`, `state`, `system`.
Across the ten frontends the usage is **0 of 4**. Meanwhile the frontends
carry their own: thirty-nine in `diagram.studio`, forty-four shadcn
primitives in `gnu.in.work`, twelve widgets in `gnosis.OS`, thirty-eight
base components in the vendored sheet, sixteen in a compiled bundle, sixty
classes in `engineering-corpus`.

The colour migration is a week's work across ten repositories. The
component migration is undefined because the system has not said what a
component *is* beyond four kernels. **Nothing else can start until the
component layer grows.**

## The rule of the flow

A token value is a number and a name. A component is code. They are not
the same kind of thing and they do not move the same way.

- **Token values, spacing steps, the family, the layer ids** are facts.
  They flow from the system to a frontend freely, and every repository
  may take them whatever its licence says.
- **Component implementations** are copied code. They flow *into* the
  system only from a repository whose licence permits it.

The system is MIT and public. Therefore:

> The system specifies; it does not copy. A frontend contributes *code* to
> the system only under a compatible licence, and contributes *decisions*
> always.

This is not a legal nicety. It is why the matrix has a licence column, and
it decides the shape of every plan below.

files, axe, thirty-six visual baselines, a severity register, six
regression gates, a registry schema — and that should flow *into* the
system, not the other way round.

`gnosis.OS` has a second problem before its licence: the root says AGPL-3.0
and forty-seven crate manifests say GPL-3.0-or-later. The root says
"02 · DISTRIBUTION — unassigned" and three component repositories return
404. The licence of that workspace is not yet a fact.

## The four decisions

These are not measurements. They are choices the owner has to make, and
each one is a decision the audit has localised.

### 1. The blue

`#3D8DCC` is the "info blue" in `gnosis.OS`'s runtime tokens, in
`gnu6-live`'s `GNU_COLORS`, and in `gnu.in.docs`' legacy sheet — while
`#4169E1` is the system's royal blue. The system's blue appears in
`gnosis.OS` in exactly two files and never in a runtime token.

**Decision:** does the system adopt a blue ramp wide enough to hold
`#3D8DCC` as a step, or is `#3D8DCC` a legacy spelling to be migrated to
royal blue? The second is cleaner but changes four repositories' idea of
their own accent.

### 2. The spacing scale

The system publishes ten steps — 4, 8, 12, 16, 24, 32, 48, 64, 96, 128.
`gnosis.OS` has the first six. `gnu6.live` declares eight steps in rem and
then **references zero of them** — the real spacing is hardcoded in
`features.css`. `gnu.in.docs` has six. `engineering-corpus` has none.

Between 20% and 38% of each frontend's length traffic already lands on the
system's scale.

**Decision:** ten steps stands, and each frontend's own scale is mapped
onto it and deleted. The `gnu6.live` case shows the cost of declaring
tokens you do not use: eight dead steps and a file full of literals.

### 3. The family

Space Grotesk in six of ten. `gnu.in.work` uses a system stack and imports
Geist and IBM Plex Sans without using them. `gnosis.OS` runs Inter, Roboto
and Montreal across three theme modules. `blob.in-showcase` uses Noto Sans
at an absolute path.

**Decision:** one family, with documented exceptions for surfaces that
deliberately differ. `spjoaillerie-live` is the case in point — a
different brand should stay a different brand, and the system needs a way
to say that without pretending to be universal.

### 4. The component layer

The blocker. See below.

## The drift has a source, and the source is upstream

The audit found that two repositories carry a `--gnosix-*` namespace that
the system does not publish: fifteen of their twenty-one names are
spelled differently, and all twenty-one values are identical. That reads
like a consumer's drift. It is not.

The vendored sheet they carry is the `gnu6-design` package, and its own
lock states where it came from: **it was cut from `Gnosix-DS-V3.4.1`** —
a release of this system from before the naming rule existed, before the
role layer existed, and before the spacing scale was published at all. It
carries the layer ids in their pre-kebab spelling and a quarter of the
palette, and three repositories vendor that one artefact:
`engineering-corpus` at `site/gnu6/`, `gnu6-docs-portal` at
`public/gnu6/`, and `gnu6-live` at `public/gnu6/`.

So the mismatch is not ten consumers drifting. It is **one stale cut of
the system's own release, vendored three times**, and the fix belongs at
the source:

1. **The system publishes the `gnu6-design` package** — or owns the cut
   that produces it. A package that carries this system's namespace must
   not be a fork of it; the two drift the moment the system moves, which
   is exactly what happened, in the one direction that is hardest to see
   because every value is still right.
2. **The package is re-cut from the current release** (4.0.0): the
   published names, the role layer, the spacing scale. One change, and
   every consumer of the vendored copy carries the published namespace.
3. **The three consumers re-vendor it**, and their locks point at the
   system's release rather than at a copy of a copy.

Until that is done, every per-consumer migration is paid twice, and the
second payment is the vendoring.

## The plan changes: two of the ten cannot be absorbed

`gnu6.live` and `gnu.in.docs` — the two the earlier plan named as the
reference consumers — are **archived and read-only**. Nothing can be
absorbed into them, so they are references and not consumers, and the
matrix says so.

The absorption was therefore rehearsed on `gnu6.live` anyway, to prove
the mechanism end to end: the design system vendored at a pinned version
and locked, the token file reduced to an alias layer over the system's
roles, several hundred literals in five stylesheets rewritten to name the
system, and the consumer's own twelve-gate chain green afterwards. The
repository is read-only, so the commit cannot be pushed and the patch is
kept in the evidence directory. The mechanism is proved; what remains is
to apply it to the repositories that accept a change.

`engineering-corpus` is the first live one, and it is the model
repository. Its own state on 2026-10-12 had been rewritten to consume
the vendored `gnu6-design` sheet, which is the drift above: its
stylesheet holds no hexadecimal colour of its own, and the twenty-one
names it carries are six of the system's and fifteen that are not. The
absorption of the corpus is therefore the *migration of the vendored
copy*, not a rewrite of the corpus's palette — which is the third step
of the fix above, and the one that pays for itself.

## The order

The order is chosen by cost per unit of risk, and by what a repository can
teach the system. It is not the order of size.

### 1. gnu6.live — the reference consumer

MIT, and already has what the others are missing: a `app/design-system/`
folder, a release dossier, a full-site manifest with sha256 digests, an
accessibility audit across sixteen routes, a visual mismatch ledger.

*Must change:* the eight `--space-*` steps it declares and never uses; the
~250 hardcoded hexes in `features.css`; its own names (`--paper`, `--ink`,
`--live`, `--os`, `--labs`) onto the system's; its `app/design-system/`
components onto the declared ones.

*Teaches:* how a release dossier should record which version of the system
a surface was built against. The system has no such field and should.

### 2. engineering-corpus — the model

MIT, public, and the repository the system's own discipline was copied
from. `scripts/qualify.py` refuses a dirty tree, clones the exact HEAD,
rebuilds twice and demands the two builds be byte-identical to the
committed `dist/`, runs negative controls, and ends on `git diff
--exit-code`. That is the shape of `ci/local-ci.sh`, and it is the standard
the other nine should be held to.

*Must change:* `site/style.css` declares a **second** `:root` that
overrides its own token file — the declared colours are the system's, the
*used* ones are a dark green set (`--mint #8DA982`, `--orange #F5A524`)
that the system does not have; thirty-five hardcoded hexes bypass the
tokens entirely; there is no spacing scale at all.

*Teaches:* it already taught the system the evidence discipline. It has
one more lesson — a token file that is overridden by the file that uses it
is a token file nobody reads.

### 3. diagram.studio

MIT, a hundred and twenty-one test files, and a verify script that runs
format, lint, typecheck, knip and the tests twice. No CI, by choice.

*Must change:* `--gnu-*` onto the system's names; the shadcn HSL set and
the `--neo-*` family, which are a second palette; the declared-but-unused
`#F7F3ED` and `#FF6A00`, which the system publishes and this frontend
declares and then never applies.

*Blocks:* the copyright is a third party's. The code can be taken with
consent; the *decisions* can be taken now.

### 4. gnu.in.work

*Must change:* `--gnu-beret` and `--gnu-orange` onto the system's names;
and the largest single job in the audit — 1966 colours outside the
contract, most of them Radix scale values across a 3039-line
`colors.css`.

*Already doing it:* `scripts/dette-couleurs.txt` — a debt baseline of
twenty-nine entries, enforced by `scripts/lint-amont.mjs` — and a
115 KB `PORTAGE.md` whose §16 is the colour-literal rule. The portage is
already under way; it just does not know the system's names yet.

### 5. gnu.in.docs

*Must change:* the five palette values under their own names onto the
system's; the `--gnu-space-1..6` scale onto the ten steps.

*Blocks:* no licence, so nothing may be taken from it. The vendored
Montreal faces are unlicensed, and the repository already records the
unresolved question in its own roadmap.

*Note:* the repository keeps the whole earlier design corpus beside the
live site — thirty-one pages, four hundred and seventy-seven uploads, the
old `_ds` sheet with a second palette and a second family. The audit
excludes that corpus, because an audit that reads the archive measures a
site that no longer ships.

### 6. gnu6-live

The hardest, and the most interesting.

*Must change:* a parallel `--ctx-*` palette that diverges from the
system's on six values; a 4853-line stylesheet that `root.tsx` does not
link and that only the tests read; `"PP Neue Montreal"` still declared in
a token file that the site does not load; and the 21 camelCase names,
which are the field's only copy of the gnosix namespace and which the
system does not publish.

*Blocks:* no licence. And its `app/design-system/` folder duplicates
`gnu6.live`'s, nearly file for file. One of the two should be deleted and
the survivor should consume the system.

### 7. gnu6-docs-portal

A static offline prototype, not a live surface, and the `gnu6-live`
specification marks it a migration donor with no new deployment. Its
content bundle is produced by `engineering-corpus`, so it is downstream of
another audited repository.

*Must change:* the 15 spellings, the 69 colours it omits, and the fact
that Space Grotesk is shipped and never applied — the `@font-face` lives
in a sheet the served chain does not link, and the motion sheets read
sixteen variables that only that sheet defines.

*Note:* the sixteen-component bundle in `spjoaillerie-live` records, in
its header, where each component came from, with source hashes. That idea
is worth taking, and it is worth taking even from a repository with no
licence, because a *technique* is not a copy.

### 8. gnosis.OS

The native consumer, and the closest thing to one.

*Must change:* `engine/blob.in/tokens.json` is already a token pipeline —
a JSON source, a codegen step, and `gen/gnu_theme.{rs,h,gpui.rs}`. It
should become a **projection of `core/TOKENS.json`**, the way
`profiles/native/` already is, rather than a fourth transcription of the
palette. `contracts/control-plane/tokens.schema.json` becomes a gate.
The `--col-layer0` / `--m3-primary` / `--r-pill` CSS-var analogue, which
is sourced from a design reference that now returns 404, should be
replaced by the system's own ids.

*Blocks:* AGPL cannot flow into an MIT repository, so the flow is one way
only. And the licence of the workspace is not yet decided.

### 9. blob.in-showcase — correct the claim, then decide

`crates/showcase/src/theme.rs:1` says the palette is read from a gnosix
path. The path exists — `gnosix/crates/gnos-ux-gpui/src/product_design.rs`
— and the palette it carries is not the system's: none of its colours is
one of ours, and the showcase's own accent is a cyan where the system has
an orange one. The claim in the source file is therefore false, and it is
false because the palette does not match, not because the path is missing.
The repository is proprietary and never published. The claim must be
corrected. After that, the question is whether this surface becomes a
consumer of `profiles/native/` — it is the only frontend the audit could
not read at all until byte-triplet colours were recognised. The decision
is that it does not: a native surface that shows a product of its own may
carry its own palette, which is what COL-004 allows, and the criterion of
absorption is a web one.

### 10. spjoaillerie-live — exclude

It is a capture of a different brand, taken because the VPS was the only
copy, with one commit, no tests, no CI, no licence, and a build that
transpiles React in the browser. Absorbing it would import Didot,
Garamond, gold and parchment into a system whose whole claim is that it
has one family and one palette.

It is excluded. One idea is taken from it — the bundle header that records
where each component came from — and the brand is left alone.

## The supply chain

The audit surfaced a structure that was not in the brief:

```
engineering-corpus ──content bundle──▶ gnu6-docs-portal
gnosix.ds ──(an older draft of the namespace)──▶ gnu6-design 1.1.1 ──vendored──▶ gnu6-docs-portal
                                                                                    gnu6-live
```

`gnu6-design 1.1.1` is a **vendored fork of the system's namespace** that
drifted in spelling and lagged by sixty-nine colours. It is the thing
that carries `--gnosix-*` into the field, and it is not the system. Two
repositories carry it, and one of them — `gnu6-live` — also carries a
duplicate of `gnu6.live`'s design-system folder.

The honest fix is to stop vendoring the namespace. The system publishes
the tokens; a frontend that needs them at build time fetches them from
the system at a pinned version, and the lock file it already keeps
(`gnu6-design.lock.json`, eleven SHA-256 entries) points at the system's
release instead. The system then has exactly one namespace, and the
"migration donor" arrangement becomes a dependency.

Note that `gnu6-docs-portal`'s `build.py` verifies its content digest and
**never verifies `gnu6-design.lock.json`**. The lock is decorative. A
lock that is not checked is a promise, not a control.

## What the system must add before any of this can start

> **This list is answered.** The naming rule is NAM-001 in the contract and
> the gate that checks it; the component layer is the contract's own, with
> the field's thirty-nine names specified against the sheet and the
> `info` accent carrying `#3D8DCC`; the consume recipe is the consumer
> gate, which reads a repository and says what it carries. What remains is
> the inventory in [`ROADMAP.md`](../../ROADMAP.md), with the numbers
> below measured before the gate learned to read the native surfaces and
> therefore to be re-measured.



1. **The naming rule, in the contract.** The rule that a published name is
   the layer id, kebab-cased, currently lives in `tools/project_tokens.py`
   — in a projection, not in the contract. That is precisely how the
   vendored copy was able to drift for so long: the rule was never
   written down, so nobody could check against it. It belongs in
   `core/rules.json`, and a gate should assert that every published name
   is derivable from the contract by that one rule.

2. **The component layer.** Four kernels against thirty-nine components in
   one frontend, sixty classes in another, thirty-eight in a vendored
   sheet. The natural expansion is the thirty-eight of the vendored sheet
   — it is the only systematic component set in the field, and it is
   already in the gnosix namespace — but it cannot be copied from two
   repositories with no licence. It has to be **specified** from the
   contract, and the two repositories migrated onto the system's own
   copies. Naming it is the work: `action`, `input`, `state`, `system`
   are too few to hold what these frontends actually build.

3. **A blue ramp that covers `#3D8DCC`**, or the decision to migrate it.

4. **A consume recipe per surface.** The system has three profiles — web,
   native, Android — and an interchange format, but no documented way for
   a consumer to pin and fetch them. `gnu6-docs-portal` already keeps a
   lock file; the system should be what it locks against.

5. **A version field for the system a surface was built against.** The
   release dossier of `gnu6.live` is the model. Without it, a consumer
   cannot say which version of the system it honours, and the audit's
   matrix cannot be recomputed against a known baseline.
